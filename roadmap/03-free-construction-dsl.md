# Этап 03 — DSL конструирования документов на Free

| Поле | Значение |
|---|---|
| Цель | Дать эргономичный встраиваемый язык построения XJDF-документов: программа описывает *что* построить, интерпретаторы решают *как* (сборка, статический анализ, журнал, а позже — эффекты) |
| Вход | Этапы 01–02 (cats, `Show`/`Eq`, валидация) |
| Выход | Новый модуль `dsl`: свободная алгебра `DocOp`, три интерпретатора (сборка в `XJDF`, план-отчёт, журнал) и синтаксический слой |
| Сложность | Высокая (ключевой этап; для FP-среднего уровня) |
| Зависимости | 01, 02 |

## Зачем это нужно

Сегодня документ собирается напрямую через конструкторы:

```scala
val doc = XJDF(
  jobId,
  NonEmptyVector.one(process),
  resourceSets = Vector(
    ResourceSet(mediaName, usage = Some(ResourceUsage.Input), resources = Vector(...)),
    ResourceSet(colorName, ...),
  ),
)
```

Это работает, но: (1) код многословен и «шумит» опциями и вложенностью; (2) намерение
(«добавь набор ресурсов Input») неотделимо от исполнения (немедленное конструирование значения);
(3) невозможно получить из программы ничего, кроме готового `XJDF` — ни план документа, ни
журнал построения, ни валидацию по шагам.

**Free-монад решает ровно это** (см. `reference/cats/docs/datatypes/freemonad.md`): программа —
это *данные* (`Free[DocOp, A]` — дерево инструкций), а выполнение — *натуральное преобразование*
(`DocOp ~> F`). Одну и ту же программу можно исполнить разными интерпретаторами.

Интуиция для новичка: программа на Free — это **список покупок**. Список можно отдать кассиру
(сборка документа), показать менеджеру (план/отчёт), записать в журнал (аудит) или отправить
курьеру (эффекты, этап 07) — сам список от этого не меняется.

## Дизайн

### 1. Алгебра (грамматика) — какие «инструкции» есть у языка

Минимальная, но честная грамматика для корневого документа:

```scala
package xjdf4s.dsl

import cats.free.Free
import xjdf4s.core.*
import xjdf4s.model.*

enum DocOp[A]:
  case SetVersion(value: Version)         extends DocOp[Unit]
  case AddComment(value: Comment)         extends DocOp[Unit]
  case AddGeneralId(value: GeneralId)     extends DocOp[Unit]
  case AddAudit(value: Audit)             extends DocOp[Unit]
  case AddProduct(value: Product)         extends DocOp[Unit]
  case AddResourceSet(value: ResourceSet) extends DocOp[Unit]
end DocOp

type DocDsl[A] = Free[DocOp, A]
```

Правила проектирования грамматики:

- одна инструкция — одно осмысленное действие (не «сеттер поля», а «добавить узел»);
- чтение (`Get*`) появляется только там, где программа реально принимает решения
  («если уже есть ресурс с таким ID, то…») — иначе держите алгебру write-only;
- не тащите в алгебру эффекты: `IO`, `Future`, исключения — их место в интерпретаторе (этап 07).

### 2. Синтаксический слой — умные конструкторы

Пользователь не видит `Free.liftF`:

```scala
object DocDsl:
  def version(v: Version): DocDsl[Unit]        = Free.liftF(DocOp.SetVersion(v))
  def comment(text: String): DocDsl[Unit]      = Free.liftF(DocOp.AddComment(Comment(text)))
  def generalId(g: GeneralId): DocDsl[Unit]    = Free.liftF(DocOp.AddGeneralId(g))
  def audit(a: Audit): DocDsl[Unit]            = Free.liftF(DocOp.AddAudit(a))
  def product(p: Product): DocDsl[Unit]        = Free.liftF(DocOp.AddProduct(p))
  def resourceSet(s: ResourceSet): DocDsl[Unit] = Free.liftF(DocOp.AddResourceSet(s))

  def resourceSet(name: Nmtoken, usage: ResourceUsage)(resources: Resource*): DocDsl[Unit] =
    Free.liftF(DocOp.AddResourceSet(ResourceSet(name, usage = Some(usage), resources = resources.toVector)))
end DocDsl
```

Программа — обычный for-comprehension:

```scala
val program: DocDsl[Unit] =
  for
    _ <- DocDsl.version(Version.V2_2)
    _ <- DocDsl.comment("Job generated by ACME MIS")
    _ <- DocDsl.resourceSet(mediaName, ResourceUsage.Input)(
           Resource(specificResource = Some(Media(MediaType.Paper, weight = Some(80)))),
         )
    _ <- DocDsl.resourceSet(colorName, ResourceUsage.Input)(...)
  yield ()
```

### 3. Интерпретатор 1 — сборка в `XJDF` через `State`

Сборка документа — это накопление: каждый `Add*` обновляет состояние. Тип интерпретатора —
`State[XJDF, *]`:

```scala
import cats.data.State
import cats.~>

val build: DocOp ~> State[XJDF, *] = new (DocOp ~> State[XJDF, *]):
  def apply[A](op: DocOp[A]): State[XJDF, A] = op match
    case DocOp.SetVersion(v)   => State.modify[XJDF](_.copy(version = Some(v)))
    case DocOp.AddComment(c)   => State.modify[XJDF](d => d.copy(comments = d.comments :+ c))
    case DocOp.AddGeneralId(g) => State.modify[XJDF](d => d.copy(generalIds = d.generalIds :+ g))
    case DocOp.AddAudit(a)     => State.modify[XJDF](d => d.copy(auditPool = d.auditPool match
      case Some(pool) => Some(pool.copy(audits = pool.audits :+ a))
      case None       => Some(AuditPool(Vector(a)))))
    case DocOp.AddProduct(p)   => State.modify[XJDF](d => d.copy(productList = d.productList match
      case Some(list) => Some(list.copy(products = list.products.append(p)))
      case None       => Some(ProductList(NonEmptyVector.one(p)))))
    case DocOp.AddResourceSet(s) => State.modify[XJDF](d => d.copy(resourceSets = d.resourceSets :+ s))

def run(program: DocDsl[Unit], seed: XJDF): XJDF =
  program.foldMap(build).runS(seed).value
```

`seed` — минимальный документ (`XJDF(jobId, types)`); программа «дозаполняет» его.
`foldMap` требует `Monad[State[XJDF, *]]` — cats даёт его сам.

### 4. Интерпретатор 2 — план-отчёт (журнал через `Writer`)

Отчёт «что сделает программа» — это интерпретатор, который не строит документ, а пишет
журнал шагов. (Вырожденный случай того же приёма — `Const[M, *]`, который хранит только
аккумулятор; он пригодится для `FreeApplicative`-анализа из п. 6. Для отчёта практичнее
`Writer`, складывающий строки в `Chain`):

```scala
import cats.data.Writer
import cats.data.Chain

val log: DocOp ~> Writer[Chain[String], *] = new (DocOp ~> Writer[Chain[String], *]):
  def apply[A](op: DocOp[A]): Writer[Chain[String], A] = op match
    case DocOp.SetVersion(v)     => Writer.tell(Chain.one(s"set version $v"))
    case DocOp.AddComment(c)     => Writer.tell(Chain.one(s"add comment: ${c.value.take(40)}"))
    case DocOp.AddGeneralId(g)   => Writer.tell(Chain.one(s"add general id ${g.usage.value}"))
    case DocOp.AddAudit(a)       => Writer.tell(Chain.one(s"add audit ${a.name}"))
    case DocOp.AddProduct(p)     => Writer.tell(Chain.one(s"add product ${p.id.fold("(unnamed)")(_.value)}"))
    case DocOp.AddResourceSet(s) => Writer.tell(Chain.one(s"add resource set ${s.name.value}"))
```

`Writer` накапливает `Chain`-журнал, значение-результат всегда `Unit`. Пока алгебра
write-only, `Get*`-веток просто нет: правило этапа — **интерпретатор — тотальная функция
над всеми инструкциями алгебры**, поэтому каждую новую инструкцию добавляют только вместе
с ветками во всех существующих интерпретаторах.

### 5. Интерпретатор 3 — валидация по шагам

Каждая инструкция валидирует добавляемый узел; результат — `Either`/`ValidatedNel`:

```scala
val validate: DocOp ~> Either[Vector[ValidationError], *] = new (DocOp ~> Either[Vector[ValidationError], *]):
  def apply[A](op: DocOp[A]): Either[Vector[ValidationError], A] = op match
    case DocOp.AddResourceSet(s) =>
      val nodeErrors = s.resources.flatMap(_.validate)
      Either.cond(nodeErrors.isEmpty, (), nodeErrors)
    case _ => Right(())
```

Это даёт dry-run: прогнать программу и получить ошибки до того, как документ собран.
(Документные проверки — дубликаты ID и т.п. — выполняет финальный `XJDF.validate` из этапа 02.)

### 6. `FreeApplicative` — когда шаги независимы

Если программа — набор независимых деклараций (типичный случай для XJDF), вместо
`Free[DocOp, A]` можно взять `FreeApplicative[DocOp, A]` (`cats.free.FreeApplicative`):
последовательность шагов без ветвлений. Выигрыш: статический анализ программы
(количество и порядок шагов известны до исполнения — например, «план-отчёт» становится
точной функцией, а не логом). Правило: начинайте с `Free` (гибкость), выносите горячие
участки в `FreeApplicative`, когда анализ окупается.

### 7. Честный разбор альтернатив (обязательный раздел для ревью)

| Подход | Плюсы | Минусы | Вердикт для xjdf4s |
|---|---|---|---|
| **Free-монад** | программа = данные: много интерпретаторов, сериализуемость плана, тесты без эффектов | алгебру надо проектировать и поддерживать; синтаксис «тяжелее» прямых вызовов | берём для публичного DSL-слоя |
| **Tagless final** (`Doc[F[_]]`) | нативный синтаксис, лучшая производительность, проще ограничивать возможности через type classes | интерпретатор выбирается *на этапе компиляции* — нельзя выполнить одну программу несколькими способами без полиморфизма | берём для внутренних абстракций транспорта (этап 06) |
| **Прямые smart-конструкторы** | ноль абстракций | нет переиспользования программ | остаётся как нижний слой API — ADT не вытесняется |

Ключевое правило этапа: **DSL — фасад над ADT, а не замена ему.** Все публичные типы модели
остаются первичным API; DSL опционален и конвертируется в ADT без потерь.

## Definition of Done

- [ ] Одна и та же программа исполняется тремя интерпретаторами; тесты доказывают разные результаты.
- [ ] Сборка через `build` даёт валидный `XJDF` (проходит `validateAll` из этапа 02).
- [ ] Журнал-интерпретатор воспроизводит порядок шагов (порядок `Vector`-вставок стабилен).
- [ ] Dry-run валидации ловит дефектный узел до сборки.
- [ ] README модуля объясняет Free-монад на примере «список покупок» и таблицу альтернатив.
- [ ] `sbt "clean ; compile ; test"` зелёный.

## Риски

- **Разрастание алгебры.** Каждое новое «удобство» = новая инструкция. Правило: инструкция
  добавляется, только если на неё есть интерпретатор в каждом существующем целевом типе.
- **Соблазн протащить IO в алгебру** (например, `LoadFileSpec`). До этапа 07 — запрещено;
  когда придёт время, это будет отдельный интерпретатор, а не новая алгебра.
- **Perf.** `foldMap` Free стекобезопасен, но строит дерево; для «горячих» мест держите
  в голове `FreeApplicative` и batch-инструкции (`AddResourceSets(Vector[...])`).
