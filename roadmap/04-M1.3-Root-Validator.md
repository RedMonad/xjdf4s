# M1.3 — Полный корневой валидатор

Статус: `[~]` переоткрыта (ряд P1 по результатам аудита)

Цель: корневой валидатор обходит весь агрегат; все SHALL реализованы;
ошибки и предупреждения разделены.

## Задачи

### M1.3-1. ID scope и target semantics (P1)
Находка: `XJDF.declaredIds` исключает `Header/@ID` и ID внутри audit
`ResourceInfo`; IDREF проверяется только по строке, не по нормативному типу цели.
Решение:
- Сделать сбор ID рекурсивным по всему instance (включая Audit Header и
  ResourceInfo ResourceSet/Resource). Проверять XML-instance uniqueness
  независимо от message-level business scope (§2.2.3).
- Ввести типизированный индекс ID targets: каждая ссылка сообщает допустимые
  виды цели; validator проверяет existence и target kind двумя issue codes.

### M1.3-2. Политика severity: ValidationReport как default (P1, решение владельца)
Находка: `validateReport` правильно разделяет severity, но `validate` превращает
любой issue в Invalid. DSL build и `ChangeOrder.applyChange` используют legacy
`validate`, поэтому SHOULD warning делает документ невалидным (вопреки ADR-0006).
Решение (подтверждено владельцем): `ValidationReport` — единственный default.
`validate` возвращает/alias к `ValidationReport`; строгая конверсия — отдельный
`validateStrict`. DSL и `applyChange` отвергают только errors.

### M1.3-3. Отделить нормативную validation от проектной политики (P1, решение владельца)
Находка: validator объявляет SHALL «Product amounts SHALL быть неотрицательными»
и «ProductList SHALL иметь хотя бы один root». В процитированных нормативных
разделах таких SHALL нет; XSD использует `xs:int` и optional `IsRoot`.
Решение (подтверждено владельцем): оформить как opt-in policy — убрать из base
XJDF conformance; при необходимости бизнес-профиль с собственной severity и
кодами, без ложных ссылок на §3.3.1.1.

### M1.3-4. Локальные SHALL Assembling/Binding (P1)
Находка: нет проверок `Container` не ссылается на родителя; `StickOn/@Face` и
`@Folio` взаимоисключающи; `BindingIntent/@ChildRefs` требует два или более;
вложенные детали не сверяются с BindingType; `BinderMaterial` должен быть закрытым.
Решение: ввести `DomainRule[(Product, Intent)]` или `checkProductIntents`:
Container≠parent; Face/Folio XOR; ChildRefs size≥2; nested detail↔BindingType;
BinderMaterial enum; SHOULD-компаньоны как warning.

### M1.3-5. Межинтентные правила уровня Product (P1)
Находка: отсутствуют проверки уникальности `Intent/@Name` в Product,
`VariableIntent/@ChildRefs` против Assembling/Binding, `ColorsUsed` subset,
`NumberOfCopies=1` для fully variable data.
Решение: одна атомарная фаза `checkProductIntentRelations`; отдельный IssueCode
на нормативную норму.

### M1.3-6. Контекстные правила Part (P1)
Находка: не проверяются `ContactType` обязательность для Contact,
`PreviewType` применимость, `SheetIndex` условие, `TileID` integer/non-negative.
Решение: `checkPartContexts` знает ResourceSet name/payload/job indexes.
Не перегружать `Part` локальным законом без контекста.

### M1.3-7. Audit-подструктуры и их правила (P1)
Находка: `DeviceInfo` теряет `Activity*`/`Event*`/`FileSpec*`/`JobPhase*`;
`ResourceInfo` теряет `Event*`/`MISDetails?`; не проверяются Level/Speed,
Types/CPI, ProcessRun chronology.
Решение: добавить недостающие children; реализовать правила только там, где
Table задаёт SHALL.

### M1.3-8. ICSVersions типизирован через IcsVersion (P1)
Находка: `XJDF/@ICSVersions` и Header/Device ICSVersions хранятся как
произвольные `NmTokens`; `IcsVersion` не применяется.
Решение: заменить на non-empty collection `IcsVersion` либо добавить total
mapping/law во всех контейнерах.

## Definition of Done M1.3
- Корневой валидатор обходит весь агрегат; все зарегистрированные правила
  вызываются из корневого обхода.
- Ошибки и предупреждения разделены; default — `ValidationReport`.
- На каждый SHALL — негативный тест.
