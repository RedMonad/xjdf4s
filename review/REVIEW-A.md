## 0. Вердикт

Сильный результат для одного милстоуна: домен не анемичный, категориальный слой
продуман и честно документирован, выбор Scala 3-конструкций в целом осмыслен,
cats используется по назначению (законы + носители `Chain`/`NonEmptyChain`).
Код читаемый, scaladoc плотный, примеры из спецификации воспроизведены.

Однако **формальный критерий готовности («`sbt test` зелёный») не выполнен и не
подтверждён**: в репозитории лежит `build.log` с падающим тестом. Кроме того,
есть **реальные отклонения от спецификации** (типы Partition Key `ProductPart`
и `Metadata`), систематическая путаница «номер раздела vs номер таблицы» в
scaladoc, и несколько конструкций, которые заявлены как несущие типобезопасность,
а на деле декоративны (`ChangeOrder`, `WithIds`/`IdAllocator`). Всё перечисленное
ниже — поправимо и не отменяет качество ядра.

## 1. Блокеры (надо закрыть до признания M0 готовым)

### 1.1 Красный тест в закоммиченном `build.log`

`build.log` фиксирует:

```
==> X xjdf4s.laws.PartitionLaws.right-biased overlay always matches the right side
Falsified after 0 passed tests.
Failed: Total 13, Failed 1, Errors 0, Passed 12
Failed tests: xjdf4s.laws.PartitionLaws
```

Это прямо противоречит DoD в `ROADMAP.md` («`sbt test` зелёный») и пункту
`[x] Feedback-итерация сборки` (в списке закрытых ошибок этого падения нет).

Важный нюанс, который усиливает замечание:

- `build.log` — это **`testQuick`** (IntelliJ), перезапустивший только
  `PartitionLaws`. Остальные сьюты (`AlgebraLaws`, `AlignmentLaws`,
  `TicketLaws`) в этом логе **не запускались вообще**, т.е. их зелёность ничем
  не подтверждена.
- Статически свойство в **текущем** коде является тавтологией: `combine`
  право-смещённый (каждое поле `b.x.orElse(a.x)`), а `matches` проверяет
  «каждый присутствующий ключ либо отсутствует у селектора, либо совпадает».
  При `combine(a,b).matches(b)` любой ключ, присутствующий справа, берётся
  именно справа, поэтому обязан совпасть. Следовательно, либо `build.log`
  устарел (зафиксировал баг, позже исправленный, но лог не перегенерирован),
  либо есть тонкая причина, которую я без компилятора не вижу.

**Действие:** прогнать полный `sbt test` на чистом кэше, зафиксировать результат
в `build.log`, а не оставлять в репозитории «красный» лог как свидетельство
сборки. Если падение воспроизводится — это приоритет №1.

### 1.2 `Part/@ProductPart` смоделирован как `IDREF`, а по спецификации — `NMTOKEN`

`reference/xjdf/6 – Resources.md`, Table 6.4:

```
| ProductPart? (Deprecated in XJDF 2.1) | NMTOKEN | References the Product/@ID
  that this Part applies to. Deprecation note: Use @Product to reference
  Product/@ExternalID. |
```

В коде же (`model/Partition.scala`):

- `productPart: Option[IdRef]` (строка 137);
- `PartitionValue.ProductRef(value: IdRef)` (строка 70);
- `type ValueOf[... ProductPart.type] => IdRef` (строка 110);
- конструктор `byProductRef(value: IdRef)` (строка 313).

Это ошибка конформности. `@ProductPart` имеет тип `NMTOKEN`, а значит **не
участвует** в механизме `ID`/`IDREF` (§2.2.3) и не должен типизироваться как
`IdRef`. Ровно так же `@Product` (ссылка на `@ExternalID`) корректно сделан
`NmToken` — `ProductPart` должен быть однотипным с ним. Косвенно это вносит
шум и в семантику `IdRef` (при будущем кодеке `ProductPart` сериализуется не как
IDREF-ссылка).

### 1.3 `Part/@Metadata` смоделирован как `NMTOKEN`, а по спецификации — `regExp`

Table 6.4:

```
| Metadata? | regExp | Metadata SHALL match metadata extracted from a PDL using
  RunList/MetadataMap or IdentificationField/MetadataMap. |
```

В коде `metadata: Option[NmToken]` (`Partition.scala:130`) и
`PartitionValue.Token` для этого ключа. Тип `regExp` — отдельный тип данных
XJDF (Appendix A, Table A.1); для него нет обёртки, и использование `NmToken`
(который валидирует «нет пробелов») заведомо ложно: регулярные выражения
содержат пробелы и спецсимволы. Минимум — завести opaque `RegExp` (или честный
`String`), а не подставлять `NmToken`.

## 2. Существенные замечания (spec-конформность и сверка с документацией)

### 2.1 Систематическая путаница «номер раздела §6.x» и «номер таблицы 6.N»

Ключевое требование задания — «сверяйся, не делай предположений» — нарушено в
scaladoc ресурсов. Семь файлов ссылаются на **номер раздела** главы 6 как на
**номер таблицы**:

| Файл | В коде | Раздел | Верная таблица |
|---|---|---|---|
| `resources/Color.scala:7` | Table 6.14 | §6.14 | **Table 6.27** |
| `resources/Finishing.scala:9` (CuttingParams) | Table 6.25 | §6.25 | **Table 6.53** |
| `resources/Finishing.scala:44` (FoldingParams) | Table 6.36 | §6.36 | **Table 6.74** |
| `resources/Layout.scala:8` | Table 6.52 | §6.52 | **Table 6.95** |
| `resources/Media.scala:8` | Table 6.57 | §6.57 | **Table 6.114** |
| `resources/NodeInfo.scala:7` | Table 6.59 | §6.59 | **Table 6.119** |
| `resources/Preview.scala:8` | Table 6.66 | §6.66 | **Table 6.134** |

При этом корректно ссылаются: `Component` (Table 6.37), `Contact` (Table 6.38),
`DeliveryParams` (Table 6.54), `Device` (Table 6.57), `RunList` (Table 6.148).
Показательно, что `Media` получил «Table 6.57» — тот же номер, что и настоящая
таблица `Device`, — т.е. ссылки не выверялись. Это ровно тот класс ошибок,
который задание просило исключить, и он же подрывает доверие к «каждый тип
ссылается на таблицу» из README.

### 2.2 `NamedColor` закрыт, а источник значений внешний и открытый

`Appendix A.2.30`: «For a list of allowed values, see [Color Names]». Код
(`prim/Enums.scala`) делает `NamedColor` **закрытым enum** из 16 «common values».
Это противоречит собственному принципу проекта (docs/02: «allowed values are» →
enum, но внешний/открытый список → `NmToken` + `Catalog`). Практическое
следствие: легальный `MediaIntent(@MediaColor="Pantone 123 C")` невозможно
выразить. Рекомендация: либо `NmToken` + `Catalog.NamedColor`, либо явно
задокументировать неполноту enum (что частично сделано, но не снимает проблему
закрытости).

### 2.3 `Header/@ID` попадает в документную область уникальности `XJDF.validate`

`XJDF.declaredIds` (`model/Ticket.scala`) собирает ID ресурсов, продуктов **и**
`auditPool...origin.id` (Header-ы аудитов). Но область уникальности
`Header/@ID` по Table 7.3 — «unique for all messages and XJMF initiated by the
Sender» (мессенджинговая), а не «в пределах одного XJDF» (§2.2.3). Два аудита с
одинаковым `Header/@ID`, но разными `Header/@Time` (легально) дадут ложное
срабатывание `checkIdUniqueness`. Одновременно `XJDF.references` **не** собирает
`IDREF` из вложенных в `AuditResource/ResourceInfo` ресурсов — асимметрия. Надо
явно решить: участвуют ли audit-Header-ы в документном ID-скоупе, и сделать
`declaredIds`/`references` согласованными.

## 3. Архитектурные наблюдения (категориальный слой)

### 3.1 `ChangeOrder = XJDF & Partial` — декоративная, а не несущая конструкция

`trait Partial` — маркер; `final case class XJDF(...) extends Partial`.
Следовательно `XJDF <: Partial`, и `XJDF & Partial ≡ XJDF`. Тип-пересечение
**не различает** change order и обычный тикет — это тот же тип. Тест в
`TicketLaws` («a change order is an XJDF refined by Partial») сам признаёт:
«the refinement is erased at the value level», и `val asXjdf: XJDF = changeOrder`
компилируется тривиально. Ни в `examples`, ни в DSL `ChangeOrder` не
используется (change order в демо сделан через `Patch`, что корректно).

Как сеньор по FP я бы честно признал: intersection type здесь — витрина фичи,
а не механизм. Настоящая типобезопасность change order уже обеспечена `Patch`
(эндоморфизм) и `mergeResourceSets` (`Ior`). Если хочется сохранить
`ChangeOrder` как тип — это должен быть **отдельный** тип (например, case class с
`Option`-полями, «relaxed cardinality» §1.6.5), а не псевдоним-пересечение.

### 3.2 `IdAllocator`/`WithIds`/`IdSource` — мёртвый код

`grep` по модулям (кроме самого `model/IdSource.scala`) не находит ни одного
использования `WithIds`, `IdAllocator`, `IdSource`. Context-function
(`IdAllocator ?=> A`) и чистый `State`-генератор существуют как демонстрация, но
DSL выделяет ID через явный параметр `id: Option[String]`, не через них. При
флаге `-Wunused:all` это не помечено (публичный API), но с точки зрения
«не анемичная модель» это бутафория. Либо подключить `IdAllocator` к DSL
(например, `dsl.inIds { ... }`), либо вынести в отдельный милстоун и не
заявлять как готовое.

### 3.3 `AmountRange.meet`/`join` — семантика и документирование расходятся

`model/.../prim/Quantity.scala`:

- `meet` для `amount` использует `stricterMin`, которая возвращает **большее**
  значение; doc-комментарий и `docs/01` утверждают «меньше обещанное
  количество». Т.е. «ужесточение» фактически *повышает* обещание — противоречие
  с описанием.
- `join` («оптимистичное расширение») для нижней границы `min` использует
  `stricterMin` (берёт максимум), т.е. **сужает** интервал — противоположно
  заявленному расширению.

Законы `Semilattice` (ассоциативность/коммутативность/идемпотентность) при этом
выполняются — каждая координата независимо есть min/max, — поэтому law-тест
`AmountRange.meet` зелёный и баг не ловит. Проблема чисто семантическая, и
усугубляется тем, что `join` **нигде не используется** и не имеет закона.
Рекомендация: уточнить определение meet/join по назначению `@MinAmount`/
`@MaxAmount` (§6.1.2) и либо исправить направления, либо переименовать/удалить
`join`.

### 3.4 Точность алгебр: `Monoid` там, где есть более сильная структура

- `Matrix` — это фактически **группа** (есть `inverse` при det≠0); `Monoid`
  занижает структуру. cats-kernel даёт `Group` — уместнее.
- `XYPair`/`Points`/`TimeSpan` — коммутативные моноиды (`CommutativeMonoid`),
  сейчас объявлены `Monoid`.
- `AuditPool`/`AmountPool` — свободный моноид над генераторами, объявлен
  `Semigroup` (без `empty`). Это **осознанно** (NonEmptyChain непустой), но
  стоит явно написать, что `Monoid` недостижим именно потому, что пустая
  история запрещена спецификацией (`T+`).

Это не ошибки, а вопрос точности описания алгебры — важный именно в свете
«категориального взгляда» как заявленной цели.

### 3.5 Оценка категориального повествования в `docs/01`

Большая часть — честная и полезная (морфизм Controller→Device, `@Types` как
слово свободной категории, `AuditPool` как свободный моноид, `Patch` как моноид
эндоморфизмов с правым действием, `snapshot: Pulse ~> NonEmptyChain` с законом
естественности — всё это **есть в коде** и покрыто свойствами). Слабое место —
§7 «Intent↔Resource Pairing = сопряжение (adjunction)»: в коде сопряжения нет
ни в каком формальном смысле (нет ни пары функторов, ни единиц/коединиц), это
лишь метафора «MIS порождает ресурсы из интента, Device забывает детали».
Аналогично `Fix[ProductTree]`+`cata` — корректно как F-алгебра, но дерево
**разворачивается** из графа ссылок (монадный unfold), и сам `ProductList`
исходно — не дерево. Это честно оговорено, но стоит снизить градус формулировок,
чтобы документ не выдавал метафору за доказанную конструкцию.

## 4. Оценка использования Scala 3 и cats

**Хорошо и по делу:**

- opaque types для всех атомарных типов Appendix A с `from`/`unsafe` и
  валидацией — образцово, без рантайм-стоимости;
- named tuples поверх opaque (`XYPair`, `Shape`, `Rectangle`, `Matrix`,
  `TimeRange`, `WorkstepKey`) — точное отражение лексики значений спецификации;
- enum (44 закрытых перечисления) + `XjdfEnum`/`XjdfEnumCompanion` — единообразно,
  и `NmToken`+`Catalog` для открытых списков — правильное различение
  (§1.10.3.1/2);
- union types (`OrientationSpec`, `NotificationDetail`, `BindingDetails`) —
  точное соответствие «не более одного из»;
- GADT-суммы (`Audit`, `ResourcePayload`, `IntentPayload`, `PartitionValue`,
  `ProductTree`);
- `ValidatedNec[Issue, Unit]` + XPath-локализация — верный выбор для
  накопительной валидации; `NonEmptyChain`/`Chain` как носители `+`/`*`.

**Спорно / требует доработки:**

- match type `ValueOf[K <: PartitionKey]` заявлен как «type-level mapping», но
  на уровне значений не используется (доступа `get[K]` нет — см. ROADMAP
  «Риски» п.3). В результате типизированные поля `Part` дублируют 27 полей
  вручную, а `ValueOf` живёт только как свидетель в одном law-тесте. Это
  честно задокументировано, но ценность конструкции низкая относительно объёма
  ручного кода.
- `Part` — case class с 27 `Option`-полями плюс параллельные `keys`/`valueOf`/
  `combine`/`PartBuilder.set`, дублирующие перечисление полей ещё четырежды.
  Это источник дрейфа: достаточно забыть поле в одном из пяти мест. Стоит
  сгенерировать/механизировать (или хотя бы добавить закон «`keys` ↔ поля
  согласованы»), иначе M3 (~130 ресурсов) унаследует ту же хрупкость.
- `Comment`, `GeneralID`, `Event`, `Milestone`, `Dependent`, `FileSpec`,
  `Disposition` лежат в `prim/Common.scala`, хотя это элементы глав 3/8, а не
  «примитивы». Разбиение `prim`/`model` местами условно (см. `docs/04`).

**cats:** используется осмысленно (`Semigroup`/`Monoid`/`Semilattice`,
`FunctionK`, `Ior`, `State`, `Show`/`Eq`/`Order`, `Chain`/`NonEmptyChain`,
`Validated`). Замечание уровня «полировка»: `Show`/`Eq` у ~30 типов написаны
вручную через `Eq.fromUniversalEquals` — это осознанное решение (документация
токенов), но оно же теряет `Order` там, где он нужен, и не даёт выводимых
инстансов.

## 6. Что не проверяемо в этой среде (и должно быть в CI)

2. Отсутствие предупреждений при `-Wunused:all` и друзьях — не подтверждено
   ничем (лог — только `testQuick` одного сьюта).

   проверено.
4. Idempotent `scalafmt` (rewrite-правила с `endMarker`/`newSyntax`) — не
   проверено, что переформатирование не меняет код повторно.
