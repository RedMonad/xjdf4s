# ADR-0005 — `Part.matches` как отношение толерантности

- **Статус:** принято (docs — PR-13, M1.5-1; законы — PR-13)
- **Дата:** 2026-08-15
- **Задача:** M1.5-1 (PR-13); дедлайн по ROADMAP §6 — «до M1.5-1»
- **Закрывает находку:** N-33
- **Связанные ADR:** ADR-0003 (форма локальных правил)

---

## Context

`docs/01` называл семантику выбора §6.1.3.2 «тонкой категорией (preorder)»:
«`part.matches(selector)` — отношение порядка (рефлексивно и транзитивно)».
Это математически неверно.

**Проверка.** `matches` рефлексивно ✅ и симметрично ✅ (по построению:
`a.matches(b) ⟺ b.matches(a) ⟺ conflictingKeys(a, b).isEmpty`), но **не
транзитивно** ❌. Контрпример:

```scala
val a = Part.bySide(Side.Front)
val b = Part.empty
val c = Part.bySide(Side.Back)
// a.matches(b) = true, b.matches(c) = true, но a.matches(c) = false
// Рефлексивно ✅, симметрично ✅, транзитивно ❌
```

Рефлексивное и симметричное, но не транзитивное отношение — **отношение
толерантности (совместимости)**, а не предпорядок.

## Decision

1. В `docs/01 §3` заменить «тонкая категория (preorder)» на отношение
   толерантности (совместимости) с явным контрпримером.
2. Настоящий частичный порядок обсуждать только через доказанное
   конфликт-свободное слияние: `a ≤ b ⟺ mergeWith(a, b).isRight &&
   merge(a, b) == b` («b продолжает a»).
3. Законы в `PartitionLaws` (PR-13):

```scala
property("Part.matches is symmetric")          // новый
property("matches(b) == conflictingKeys(b).isEmpty")  // закон-мост (уже был)

test("Part.matches is a tolerance relation (reflexive, symmetric, non-transitive)")
property("merge-derived order is reflexive")   // новые
property("merge-derived order is antisymmetric")
property("merge-derived order is transitive")
```

## Alternatives

| Вариант | Суть | Оценка |
| --- | --- | --- |
| Оставить «preorder» | Ноль работы | Ложное утверждение в документации; нарушает правило «законы важнее названий» |
| Объявить структуру-обёртку, где `matches` транзитивно | Искусственная категория | Не соответствует коду и §6.1.3.2; транзитивного замыкания в модели нет |
| **Отношение толерантности + merge-порядок** | Принято | Честно описывает код; законы проверяются |

## Consequences

- `docs/01` больше не утверждает ложного порядка; каждое утверждение имеет
  закон либо пометку «эвристика» (конвенция M1.5-1).
- Симметричность `matches` — теперь закон, а не наблюдение.
- Выбор раздела §6.1.3.2 остаётся без изменений: итерация сверху вниз,
  первый совпавший ресурс.

## Migration impact

Нет: изменения — только документация и законы, публичный API не тронут.

**Срок пересмотра:** если в M1.6/M3 появится реальная потребность в
частичном порядке разделов (например, иерархия выборки), порядок вводится
через доказанное `merge`, а не переобъявлением `matches`.
