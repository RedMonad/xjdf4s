# Free-DSL для конструирования XJDF

Почему и как устроен слой `dsl`. Документ меняется только вместе с дизайном DSL; пошаговые детали
внедрения — в [roadmap/03](../roadmap/03-free-construction-dsl.md).

## Зачем

Прямое конструирование `XJDF` работает, но сливает три разных дела: *намерение* («добавь набор
ресурсов Input»), *исполнение* (немедленная сборка значения) и *наблюдение* (что программа собиралась
сделать). Free-монад разводит их: программа — **данные** (`DocDsl[A] = Free[DocOp, A]`), исполнение —
**интерпретатор** (`DocOp ~> F`), наблюдателей можно добавлять, не трогая программы.

Одна программа — много исполнений (тесты `DocDslChecks`):

| Интерпретатор | Целевой тип | Результат |
|---|---|---|
| `buildDocument` | `State[XJDF, *]` | готовый документ |
| `traceProgram` | `Writer[Chain[String], *]` | трасса шагов |
| `validateSteps` | `Either[Vector[ValidationError], *]` | dry-run валидация |

## Алгебра

```scala
enum DocOp[A]:
  case SetVersion(value: Version)         extends DocOp[Unit]
  case AddComment(value: Comment)         extends DocOp[Unit]
  case AddGeneralId(value: GeneralId)     extends DocOp[Unit]
  case AddAudit(value: Audit)             extends DocOp[Unit]
  case AddProduct(value: Product)         extends DocOp[Unit]
  case AddResourceSet(value: ResourceSet) extends DocOp[Unit]
```

Алгебра **write-only**: каждая инструкция — одно действие «добавить узел», результатов-значений нет
(все `Unit`), поэтому `Functor[DocOp]` — тождественное отображение, типизированное GADT-уточнением.
Read-инструкции (`Get*`) появятся только когда появится реальный сценарий «прочитать текущее состояние
и принять решение» — каждая новая инструкция обязана получить ветку во **всех** интерпретаторах.

## Программа

```scala
val program: DocDsl[Unit] =
  for
    _ <- DocDsl.version(Version.V2_2)
    _ <- DocDsl.comment("Job generated by ACME MIS")
    _ <- DocDsl.resourceSet(mediaName, ResourceUsage.Input)(
           Resource(specificResource = Some(Media(MediaType.Paper, weight = Some(80)))),
         )
  yield ()

val document: XJDF = DocInterpreters.run(program, seed)   // seed: XJDF(jobId, types)
```

## Инварианты

1. **DSL — фасад над ADT.** Все значения программы — значения модели; DSL ничего не дублирует и
   ничего не теряет (`run` даёт обычный `XJDF`, проходящий `validateAll`).
2. **Интерпретатор — тотальная функция** над всеми инструкциями алгебры; компилятор (exhaustivity)
   ловит неполноту.
3. **Программа чистая.** Эффекты (`IO`) появятся на этапе 07 и только как новый интерпретатор;
   алгебра не меняется.
4. **Сборка сохраняет порядок шагов** (`Vector :+`), трасса воспроизводит этот порядок.

## Free vs tagless vs прямые конструкторы

| Подход | Плюсы | Минусы | Роль в xjdf4s |
|---|---|---|---|
| Free | программа = данные: много интерпретаторов, replay, тесты без эффектов | алгебру надо проектировать и поддерживать | публичный DSL-слой |
| Tagless final | нативный синтаксис, быстрее | интерпретатор фиксируется при компиляции | внутренние capability транспорта (этап 06) |
| Прямые конструкторы | ноль абстракций | нет переиспользования программ | нижний слой API — ADT остаётся первичным |

## Расширение алгебры

Добавить инструкцию = (1) case в `DocOp`, (2) smart-конструктор в `DocDsl`, (3) ветки во всех
интерпретаторах, (4) тест каждой ветки. Если инструкция не нужна хотя бы двум интерпретаторам —
она не нужна в алгебре.

Понятийный минимум (Functor/Monad/Free/State/Writer) — [fp-glossary.md](fp-glossary.md).
